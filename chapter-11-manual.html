What You'll Learn

🎯 Chapter Objectives

After studying this chapter, you will understand the purpose and characteristics of three types of fact tables. Each solves different analytical challenges, and mastering all three is essential for designing effective dimensional models.

📌 The Three Types of Fact Tables

  • Transaction Fact Table Most Common — Tracks individual activities/events that define a business process
  • Periodic Snapshot Fact Table For Status — Periodically samples status measurements like balances or inventory levels
  • Accumulating Snapshot Fact Table For Workflows — Tracks progress of an item through a series of processing steps

Some business processes may require only one kind of fact table, but others will require two or more working together. This chapter arms you with an understanding of the capabilities of each, so you can choose the right design for every situation.

Why This Matters

In real-world data warehouses, using the wrong type of fact table is one of the most common mistakes. It leads to complex queries, poor performance, and frustrated business users. Understanding these three patterns will make you a more effective data modeler.

Transaction Fact Tables

Transaction fact tables are the most common type you'll encounter. They capture details about events or activities — things that happen at a specific point in time. By storing facts and associated dimensional detail, they allow activities to be studied individually and in aggregate.

What is a Transaction?

The word "transaction" has a formality to it and connotes the exchange of goods, services, or money. But in fact, any kind of event can be considered a transaction:

  • Booking an order
  • Shipping a product
  • Making a payment
  • Phone calls from customers
  • Student attendance logging

Although no money passes hands in some cases, these activities can still be modeled as transactions.

Three Key Properties

1. Grain of Transaction Fact Tables

The grain can be declared in two ways:

  • By business artifact: "One row per order line" or "One row per transaction"
  • Dimensionally: "Orders by day, customer, product, and salesperson"

Important Note

Although the word "transaction" appears in its name, a transaction fact table's grain is not always the individual transaction. Many real-world fact tables summarize activities — combining multiple transactions into single rows when they share the same dimensional values.

2. Transaction Fact Tables Are Sparse

This is crucial: rows are recorded only for activities that take place, not for every possible combination of dimension values.

Example

An orders fact table does NOT record rows each day for every combination of salesperson, product, and customer. That would lead to excessive growth and clutter reports with zero-valued rows. Instead, rows are only recorded when orders actually occur.

3. Transaction Fact Tables Contain Additive Facts

Transaction fact tables normally record fully additive facts — measurements that can be summed across all dimensions.

Handling Non-Additive Facts

Most nonadditive measurements, such as ratios, should be broken down into fully additive components. For example, instead of storing "margin rate" (10%), store the components:

  • margin_dollars — fully additive
  • order_dollars — fully additive

Then compute the ratio after aggregation: You want the ratio of the sums, not the sum of the ratios!

Step 3: SQL Queries You Can Write

-- Query 1: Total sales by product category for January 2024 SELECT p.category_name, SUM(f.quantity_sold) AS total_units, SUM(f.net_sales_amount) AS total_revenue, SUM(f.gross_profit) AS total_profit FROM order_line_facts f JOIN product_dim p ON f.product_key = p.product_key JOIN date_dim d ON f.date_key = d.date_key WHERE d.year_month = '2024-01' GROUP BY p.category_name ORDER BY total_revenue DESC;
-- Query 2: Promotional effectiveness analysis SELECT pr.promotion_name, pr.discount_type, COUNT(DISTINCT f.order_id) AS orders_using_promo, SUM(f.discount_amount) AS total_discounts_given, SUM(f.net_sales_amount) AS revenue_with_promo, SUM(f.gross_profit) AS profit_with_promo FROM order_line_facts f JOIN promotion_dim pr ON f.promotion_key = pr.promotion_key WHERE pr.promotion_key != 0 -- Exclude "No Promotion" GROUP BY pr.promotion_name, pr.discount_type;

Why These Queries Work

Because all facts are fully additive, we can freely SUM them across any dimension. The margin rate isn't stored directly — instead, we store net_sales_amount and gross_profit, then calculate margin after aggregation:

Margin Rate = SUM(gross_profit) / SUM(net_sales_amount)

Periodic Snapshot Fact Tables

Sometimes, measuring the effect of a series of transactions is as useful as measuring the transactions themselves. These effects are called status measurements.

The Challenge: Studying Status

Common status measurements include:

  • Account balances — the cumulative effect of deposits and withdrawals
  • Inventory levels — deliveries minus removals
  • Water level in a reservoir
  • Temperature readings

Why Transaction Tables Fall Short

Computing balance from transaction history can be inefficient:

  • An account open for 50 years might require aggregating thousands of transactions
  • To get total deposits for all customers, you'd have to do this for every account
  • Some measurements (like temperature) have no corresponding transactions at all

Don't Store Balance with Each Transaction!

You might think: "Why not just add a balance column to the transaction fact table?" This approach has two critical problems:

📌 Problems with Storing Balance in Transaction Facts

  • Problem 1: Sparsity — If there's no activity on a day, there's no row to record the balance. Finding the balance would require searching backward through time.
  • Problem 2: Double-counting — If there are multiple transactions on the same day, the balance would appear multiple times, causing queries to double-count.

Golden Rule

Storing a transaction and its effect (balance) in the same row of a fact table is always problematic. When you need to study status measurements, use a separate snapshot fact table.

The Snapshot Model

A periodic snapshot fact table samples the measurement in question at a predetermined interval. This makes it easy to study status without aggregating long chains of transaction history.

Semi-Additivity

This is one of the most important concepts to understand about snapshots:

Semi-Additive Facts Cannot Be Summed Across Time

If you have $100 in your account at the end of each day of the week, that does NOT mean you have $700 at the end of the week! Your account balance is not additive across time.

However, the balance IS additive across other dimensions — you CAN add together balances from multiple accounts on the same day.

While semi-additive facts can't be summed across time, they can be meaningfully summarized using:

  • Average — Average daily balance
  • Minimum — Lowest balance in period
  • Maximum — Highest balance in period
  • Last — Period-end balance

  • Sum of daily balances: Allows computing average balance across aggregations
  • Fully additive facts: Transaction counts and dollar amounts summarize the period's activity
  • Period-to-date facts: YTD, QTD, MTD measurements

Period-to-Date Measurements

A snapshot is the logical home for period-to-date measurements (MTD, QTD, YTD, lifetime-to-date). Like balances, these:

  • Measure cumulative effect of activities
  • Are NOT additive across time
  • Cannot be stored reliably with transactions

Snapshots and Slow Changes

Important Rule for Type 2 Changes

A periodic snapshot records only one row for each combination of natural keys in the dimensions that define its grain. When a dimension undergoes a Type 2 slow change (creating multiple rows for the same entity), the snapshot should only reference the version that was current at snapshot time. Recording more than one would cause double-counting!

Step 4: SQL Queries for Inventory Analysis

-- Query 1: Total inventory value across all stores for a specific date -- This works because inventory_value IS additive across stores SELECT d.full_date, p.category_name, SUM(f.quantity_on_hand) AS total_units, SUM(f.inventory_value_cost) AS total_value FROM inventory_daily_snapshot f JOIN date_dim d ON f.date_key = d.date_key JOIN product_dim p ON f.product_key = p.product_key WHERE d.full_date = '2024-01-21' GROUP BY d.full_date, p.category_name;

Wrong Query Alert!

The following query is INCORRECT — it sums inventory across time:

-- ❌ WRONG! This sums inventory across days SELECT p.product_name, SUM(f.quantity_on_hand) AS total_inventory -- WRONG! FROM inventory_daily_snapshot f JOIN product_dim p ON f.product_key = p.product_key JOIN date_dim d ON f.date_key = d.date_key WHERE d.year_month = '2024-01' GROUP BY p.product_name; -- This would give you 150+138+123+305+... = 1,526 units -- But you never had 1,526 units!
-- ✅ CORRECT: Use AVG for average inventory over time SELECT p.product_name, AVG(f.quantity_on_hand) AS avg_daily_inventory, MIN(f.quantity_on_hand) AS min_inventory, MAX(f.quantity_on_hand) AS max_inventory FROM inventory_daily_snapshot f JOIN product_dim p ON f.product_key = p.product_key JOIN date_dim d ON f.date_key = d.date_key WHERE d.year_month = '2024-01' GROUP BY p.product_name;

Calculating Average Across Multiple Aggregation Levels

When you need average inventory across BOTH time AND another dimension (like category), store sum_daily_inventory and days_count so you can calculate: AVG = SUM(sum_daily_inventory) / SUM(days_count)

📌 Periodic Snapshot Design Checklist

  • ✅ Define snapshot period — Daily, weekly, monthly?
  • ✅ Identify what's being sampled — Account, product, location?
  • ✅ Label semi-additive facts clearly — Document what can't be summed
  • ✅ Add embellishments for usability — Period-begin, period-end, sums for averaging
  • ✅ Include additive activity facts — What happened during the period
  • ✅ Handle Type 2 changes correctly — Only current surrogate key per natural key
  • ✅ Ensure density — One row per period per entity, even without activity

🔑 Snapshot Fact Table Key Takeaways

  • Samples status measurements at predetermined intervals
  • Grain = period + what is being sampled
  • Dense — rows exist for every period, regardless of activity
  • Contains semi-additive facts (can't sum across time)
  • Can be embellished with period-begin, period-end, and additive summary facts
  • Only one row per natural key combination (to avoid double-counting)

Accumulating Snapshot Fact Tables

The third type of fact table is used when you need to track the progress of an item through a series of processing steps and analyze the elapsed time between events.

The Challenge: Studying Elapsed Time

Many business processes can be described as a series of stages or steps:

Submitted → Reviewed → Processed → Underwritten → Settled

Common examples include:

  • Manufacturing: ordered → manufactured → QA'd → packaged → shipped
  • Mortgage processing: submitted → reviewed → processed → underwritten → settled
  • Technical support: logged → assigned → diagnosed → closed

The efficiency of a process is often measured by how long it takes to complete steps:

  • Average days between order and shipment
  • Time from application to settlement, grouped by loan type
  • How long tickets spend in each status

Where Transaction Tables Fall Short

You could track status changes in a transaction fact table (one row per status change), but this creates problems:

The Correlated Subquery Problem

To figure out how long it took to review an application requires computing elapsed days between submission and approval — but these are in separate rows. For a group of applications, this requires a correlated subquery — complex to write and poor performing.

What About Begin and End Dates?

Adding begin/end dates for each status helps for adjacent stages, but:

  • Doesn't help when processes aren't linear (items can go back to prior stages)
  • Doesn't help when measuring time across multiple stages (e.g., submission to settlement)

The Accumulating Snapshot Design

An accumulating snapshot is fundamentally different from other fact tables:

📌 Unique Characteristics

  • One row per identifiable entity being processed (application, order, ticket)
  • Rows are UPDATED as the process unfolds (unlike other fact tables!)
  • Multiple date keys — one for each major milestone
  • Elapsed time facts — days spent at each stage

Life Cycle of a Row

Unlike other fact tables, accumulating snapshot rows are updated regularly. Here's how a single row evolves:

Day 1 — Application Submitted

Row inserted with day_key_submitted = today. Other date keys = 0 (special "not yet" value). days_reviewing = 0.

Day 2 — No Status Change

days_reviewing incremented to 1. Application still under review.

Days 3-9 — Still Under Review

days_reviewing continues incrementing daily.

Day 10 — Review Complete

day_key_reviewed = today. days_reviewing = 9 (final). review_amount = $90,000 (officer changed amount). Now days_processing starts incrementing.

Day 11+ — Processing Stage

days_processing increments daily until next milestone...

"Lags" Between Milestones

The elapsed time facts are sometimes called "lags" because they represent elapsed time between milestones. days_reviewing could also be named lag_submitted_reviewed. Naming after the stage is more flexible for nonlinear processes.

Pairing Transaction and Accumulating Snapshots

Transaction and accumulating snapshot models complement each other beautifully:

Transaction Star Accumulating Snapshot
Study processing volumes at each step Study elapsed time between steps
Analyze workload by stage Measure process efficiency
One row per status change One row per entity (updated)

Best Practice

If you build both, design the accumulating snapshot to use the transaction star as its source. Both can connect to the operational system, but using the transaction star as the source simplifies ETL and eliminates redundancy.

R7: Credit fee received
R8: Credit report ordered
U1: Forwarded to underwriter→PROCESSED (Underwriting stage)

Handling Nonlinear Processes

Many processes aren't strictly linear — items may skip steps or return to prior stages:

Submitted → Reviewed → Submitted → ...

Application returned due to missing signature

📌 Rules for Nonlinear Processes

  • Elapsed time: If application returns to "Submitted," resume incrementing days_reviewing
  • Milestone dates: Work with business to define rules:
    • Submission date = earliest date status was assigned?
    • Approval date = latest date approval was granted?
  • These are business decisions, not technical ones — let business users decide

Slow Changes in Accumulating Snapshots

Critical Rule for Type 2 Changes

The accumulating snapshot should contain only one row per natural key of the defining dimension. When a Type 2 change occurs:

  • The dimension table will have multiple rows (old and new version)
  • The fact table should be updated with the most recent surrogate key
  • Never use natural keys in accumulating snapshots — this would cause double-counting

Side Effect to Expect

Because of this, the dimension table may have more rows than the fact table. This is correct and expected! It can pose tuning challenges — star-join optimization may not be the most efficient approach for queries on accumulating snapshots.

-- Query 2: Find bottlenecks — which stage takes longest? SELECT 'Payment to Pick' AS stage, ROUND(AVG(hours_to_pick), 1) AS avg_hours FROM order_fulfillment_facts WHERE date_key_delivered != 0 UNION ALL SELECT 'Pick to Pack' AS stage, ROUND(AVG(hours_to_pack), 1) AS avg_hours FROM order_fulfillment_facts WHERE date_key_delivered != 0 UNION ALL SELECT 'Pack to Ship' AS stage, ROUND(AVG(hours_to_ship), 1) AS avg_hours FROM order_fulfillment_facts WHERE date_key_delivered != 0 UNION ALL SELECT 'Ship to Deliver' AS stage, ROUND(AVG(hours_in_transit), 1) AS avg_hours FROM order_fulfillment_facts WHERE date_key_delivered != 0 ORDER BY avg_hours DESC;
-- Query 3: Orders currently stuck at each stage SELECT s.status_name AS current_stage, COUNT(*) AS orders_stuck, ROUND(AVG( CASE WHEN s.status_name = 'Placed' THEN hours_to_payment WHEN s.status_name = 'Confirmed' THEN hours_to_pick WHEN s.status_name = 'Picked' THEN hours_to_pack WHEN s.status_name = 'Packed' THEN hours_to_ship WHEN s.status_name = 'Shipped' THEN hours_in_transit END ), 1) AS avg_hours_waiting FROM order_fulfillment_facts f JOIN order_status_dim s ON f.current_status_key = s.status_key WHERE f.date_key_delivered = 0 -- Not yet delivered GROUP BY s.status_name ORDER BY orders_stuck DESC;

Combining with Transaction Fact Table

A companion transaction fact table would track each status change event (one row per status change). This lets you analyze:

  • Transaction Star: "How many claims were validated on Monday?" (volume by stage)
  • Accumulating Snapshot: "How long does validation take on average?" (elapsed time)

🔄 Step-by-Step: Building an Accumulating Snapshot ETL

Here's a simplified view of how the ETL process works for an accumulating snapshot:

Step 1: Initial Insert

When a new entity (order, claim, application) is created in the source system, INSERT a new row into the fact table. Set the first milestone date, leave other dates as 0 (or a special "Not Yet" date key), and initialize elapsed time facts to 0.

Step 2: Daily "Aging" Update

Each day, UPDATE all in-progress rows to increment the current stage's elapsed time. For example, if an order is "Picked" but not yet "Packed", increment hours_to_pack by 24.

Step 3: Milestone Update

When an entity reaches a new milestone, UPDATE the row: set the milestone date key, finalize the previous stage's elapsed time, and begin tracking the new stage.

Step 4: Handle Reversals

If an entity returns to a prior stage (e.g., order sent back to warehouse), resume incrementing that stage's elapsed time. Work with business to define rules for how dates should be handled.

ETL Complexity Warning

Accumulating snapshots are the most complex fact tables to load because they require UPDATEs rather than just INSERTs. Plan your ETL carefully:

  • Use efficient UPDATE strategies (indexes on natural keys)
  • Consider batch processing for "aging" updates
  • Log all changes for audit purposes
  • Have rollback procedures for failed loads

📌 Accumulating Snapshot Design Checklist

  • ✅ Identify the process and entity — What moves through stages? (order, claim, ticket)
  • ✅ Define major milestones — Don't track every status, just key business events
  • ✅ Create multiple date role-playing dimensions — One per milestone
  • ✅ Add elapsed time facts — Track time at each stage
  • ✅ Handle "Not Yet" dates — Use 0 or a special date key for incomplete milestones
  • ✅ Plan for nonlinear processes — Define rules for reversals and skipped stages
  • ✅ Design ETL for UPDATEs — More complex than insert-only fact tables
  • ✅ Consider a companion transaction star — For volume analysis by stage

🔑 Accumulating Snapshot Key Takeaways

  • Tracks progress through processing steps
  • Grain = one row per identifiable entity (application, order, ticket)
  • Rows are regularly UPDATED — unique among fact tables
  • Multiple milestone date keys — one per processing stage
  • Elapsed time facts track days at each stage
  • Pairs well with transaction stars — each answers different questions
  • Focus on key business milestones, not all operational statuses
  • For Type 2 changes: update to most recent surrogate key

When to Use Each Type

Use Transaction Fact Table When...

  • You need to track individual events or activities
  • You want to aggregate activities by various dimensions
  • You need granular drill-down capability
  • Questions are about "how many" and "how much"

Use Periodic Snapshot When...

  • You need to track status measurements (balances, levels, inventory)
  • Computing status from transactions would be inefficient
  • Status has no corresponding transactions (temperature, etc.)
  • Questions are about "what was the balance/level at point X"

Use Accumulating Snapshot When...

  • Items move through defined processing stages
  • You need to measure elapsed time between stages
  • Individual items can be uniquely identified
  • Questions are about "how long does it take" and "where are delays"

Remember: You Can Combine Them!

It's not an either/or decision. A single business process may need two or even all three types of fact tables working together. The inventory process, for example, can benefit from a transaction star (track shipments), a periodic snapshot (track levels), and an accumulating snapshot (track order fulfillment stages).

Quick Reference: Fact Table Selection Guide

📌 Use TRANSACTION when you need to...

  • Count or sum activities (orders, shipments, calls)
  • Drill down to individual events
  • Aggregate by any combination of dimensions
  • Answer "how many" or "how much" questions

📌 Use PERIODIC SNAPSHOT when you need to...

  • Track status or levels over time (inventory, balances)
  • Compare status at different points in time
  • Calculate averages, minimums, or maximums over periods
  • Answer "what was the level" questions

📌 Use ACCUMULATING SNAPSHOT when you need to...

  • Track items through defined processing stages
  • Measure elapsed time between milestones
  • Identify bottlenecks and process inefficiencies
  • Answer "how long" or "where are delays" questions

Chapter Summary

🎓 What You've Learned

This chapter introduced the three fundamental types of fact tables in dimensional modeling. Each serves a distinct analytical purpose, and mastering all three is essential for effective data warehouse design.

Key Points to Remember

📌 Transaction Fact Tables

  • Track events — grain corresponds to individual transaction or summary
  • Sparse — rows only for actual activities
  • Contain fully additive facts
  • Most common fact table type

📌 Periodic Snapshot Fact Tables

  • Sample status at predefined intervals across specified dimensions
  • Dense — unlike transaction tables
  • Contain semi-additive facts (can't sum across time)
  • Can be embellished with period-begin, period-end, and additive summary facts
  • One row per combination of natural keys (avoid double-counting)

📌 Accumulating Snapshot Fact Tables

  • Track progress through processing steps — one row per entity
  • Rows are repeatedly updated as process unfolds
  • Multiple day_keys represent milestone achievements
  • Facts record elapsed time at each stage
  • For Type 2 changes: use most recent surrogate key

Final Advice from Your Senior Architect

🏆 Remember these principles:

  1. Know your analytical requirements first. The right design depends on what questions the business needs to answer.
  2. Don't force one type to do another's job. If you find yourself writing complex queries with correlated subqueries, you probably need a different fact table type.
  3. Multiple fact tables can work together. Transaction and accumulating snapshots complement each other beautifully — don't be afraid to use both.
  4. Never store balances with transactions. This is one of the most common mistakes — it always leads to problems.
  5. Be careful with Type 2 changes. Always use the most recent surrogate key to avoid double-counting.

📚 Glossary of Key Terms

Term Definition Example
Grain The level of detail represented by a single row in a fact table "One row per order line item" or "Daily balance by account"
Additive Fact A measurement that can be summed across ALL dimensions Sales amount, quantity sold, shipping cost
Semi-Additive Fact A measurement that can be summed across SOME dimensions (not time) Account balance, inventory level, portfolio value
Non-Additive Fact A measurement that cannot be meaningfully summed Ratios, percentages, unit prices
Sparse Rows exist only when events occur (transaction tables) No order on Tuesday = no row for Tuesday
Dense Rows exist for every period regardless of activity (snapshots) Row for every day, even if balance unchanged
Degenerate Dimension A dimension key stored directly in the fact table (no separate table) Order number, invoice number, transaction ID
Surrogate Key A system-generated key used to join fact and dimension tables customer_key = 12345 (not the business customer ID)
Role-Playing Dimension Same dimension used multiple times with different meanings DATE_DIM as order_date, ship_date, delivery_date
Milestone A significant stage in a process (accumulating snapshots) Submitted, Approved, Shipped, Delivered
Lag Elapsed time between two milestones Days from submission to approval
Type 2 SCD Slowly Changing Dimension that creates new rows for changes Customer moves → new row with new address, old row preserved

⚠️ Common Mistakes to Avoid

Top 5 Rookie Mistakes

  1. Storing balance with transactions — Always use a separate snapshot table for status measurements
  2. Summing semi-additive facts across time — Balance + Balance ≠ Meaningful number. Use AVG, MIN, MAX instead
  3. Storing ratios in fact tables — Break them into additive components (numerator and denominator)
  4. Using natural keys with Type 2 dimensions — Always use surrogate keys to avoid double-counting
  5. Making snapshots sparse — Snapshots should be DENSE (one row per period, even without activity)
