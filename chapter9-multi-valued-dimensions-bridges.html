🎯 What You'll Learn

In the real world, data relationships aren't always simple. Sometimes a fact needs to relate to multiple dimension values, or a dimension needs to store multiple values for a single attribute. This chapter teaches you how to handle these complex scenarios using bridge tables.

Think of bridge tables as a double-edged sword: they provide ultimate power and flexibility, but come with risks. The most significant risk is double-counting – producing inaccurate results if the schema is misused.

Why This Matters

Many organizations refuse to use bridge tables due to the risk of errors. However, dismissing them entirely may severely limit your analytic capabilities. Before making that decision, you must understand bridges fully.

Two Main Challenges We'll Address

  1. Multi-valued dimensions: When a fact table row needs to reference more than one row in a dimension table
  2. Multi-valued attributes: When a dimension row needs to capture multiple values for a single attribute

Standard One-to-Many Relationships

Before we dive into complex scenarios, let's remind ourselves of the standard relationship pattern that has worked so well in star schemas.

The Golden Rule (Until Now)

Every fact has been related to exactly one instance of each dimension. An order relates to exactly one product. A sale relates to exactly one customer. This creates the clean, powerful star configuration.

This relationship type is called one-to-many (also known as master-detail or parent-child):

  • Each dimension row may be related to zero or more fact rows
  • Each fact row must be related to exactly one row in each dimension table

Why One-to-Many Works So Well

The standard query pattern relies heavily on this one-to-many relationship:

SELECT 
  product.brand_name, 
  SUM(order_facts.order_dollars) 
FROM 
  product, order_facts 
WHERE 
  product.product_key = order_facts.product_key 
GROUP BY 
  product.brand_name

This works perfectly because each order relates to one and only one brand_name.

The Challenge: What If Multiple Salespeople Collaborate?

But what happens when reality isn't so simple? What if more than one salesperson can collaborate on an order? The standard star schema can't handle this – the fact table can't hold multiple salesrep_keys!

Multi-Valued Dimensions

A multi-valued dimension occurs when a single fact table row may need to relate to multiple rows in a dimension table. For example, multiple salespeople may collaborate on a single order.

The Problem Illustrated

In our order_facts example: Most orders have one salesperson. But some orders have two, three, or any number of salespeople working together. The standard foreign key approach breaks down because we can only store ONE salesrep_key in the fact table.

Option 1: Simplifying the Relationship

The simplest approach is to decompose the many-to-many relationship into two or more one-to-many relationships using dimension roles.

Limitations of the Simplified Approach

Problem Impact
Fixed Number of Relationships If you design for 2 salespeople, what happens when 3 collaborate? You'll eventually hit a limit.
Reporting Complications A simple question like "What are the total order_dollars for Ann?" becomes complex. Ann might be the primary or secondary salesperson!
Grouping Challenges Grouping facts by salesperson is difficult because the same salesperson could appear in different columns.
When Simplification Works

This approach may be acceptable if: (1) collaboration is rare, (2) you can limit to a fixed number of participants, and (3) most reporting focuses on the primary role. Skilled analysts can handle occasional complex reports.

Option 2: Using a Bridge Table

A bridge table sits between the fact table and the dimension table, allowing any number of relationships. This is the powerful (but dangerous) solution.

How a Bridge Table Works

  1. Create a group table (the bridge) with a group_key and a foreign key to the dimension
  2. For each group of collaborators, add one row per member, all sharing the same group_key
  3. The fact table references the group_key instead of the dimension directly
  4. Join fact → bridge → dimension to access the dimension attributes

Key Insight

The bridge table can accommodate groups of any size. If 15 salespeople collaborate, you simply add 15 rows with the same group_key. Even solo sales need a group – it just has one row!

⚠️ Bridges and Double-Counting

Here's the dangerous part. Because a fact can now relate to multiple dimension rows, you risk counting the same fact multiple times!

The Double-Counting Danger

Ann and Henry's $1,000 order is associated with both of them. If you query orders by region, that same $1,000 will be counted twice – once for Ann, once for Henry. If three people collaborated, it would be triple-counted!

When Double-Counting Is Actually Wanted

Sometimes, you want this behavior! This is called an impact report:

Impact Report Use Case

"Show me total order_dollars by salesperson" – Here, we want Ann and Henry's joint order counted for both. It shows the sales volume each person was involved in.

Other examples: total claim dollars by party, total office visits per diagnosis.

However, it's a serious error to take that report and produce a grand total. Ann's $1,000 + Henry's $1,000 ≠ $2,000 in actual orders!

SELECT 
  salesrep.region, 
  SUM(order_facts.order_dollars) 
FROM 
  salesrep, sales_group, order_facts 
WHERE 
  order_facts.sales_group_key = sales_group.sales_group_key AND 
  sales_group.salesrep_key = salesrep.salesrep_key 
GROUP BY 
  salesrep.region

This query groups by region, not individual salespeople. Since Ann and Henry are both in "East," their joint order gets counted twice for the East region! ❌

Safe Impact Reports

The only safe way to construct an impact report is to group by a column that has a unique value for each group member – usually the natural key or salesperson_name.

Solution 1: Adding an Allocation Factor

One way to eliminate double-counting is to add an allocation factor to the bridge table. This indicates what percentage of the fact should be credited to each group member.

SELECT
  salesperson_name,
  SUM(order_dollars * allocation) AS allocated_dollars
FROM ...

-- Result:
-- Ann Davis     750
-- Henry Perez   250
-- Grand Total: 1,000 ✓
Allocation Challenges
  • Often no allocation rule exists – How do you allocate a healthcare charge across multiple diagnoses?
  • Must be business-approved – Technical teams shouldn't invent allocation rules
  • Some facts can't be allocated – If Ann and Henry sold ONE refrigerator, allocating gives Ann 0.75 refrigerators! 🤔

  • The bridge tables are hidden from inexperienced users

Slow Changes with Bridges

As with any snowflaked design, bridges require careful attention to slowly changing dimensions.

Change Type What Happens
Type 1 Change (overwrite) If Ann's attributes are updated, she remains in her existing groups. No action needed on the bridge. ✓
Type 2 Change (add new row) A new surrogate key is created for Ann. The next time Ann and Henry collaborate, a new group must be created.
Group Membership Changes If Henry leaves the team and two new people join:
• Type 1: Delete Henry's row, add two new rows
• Type 2: Create an entirely new group with the new membership
When Groups Are Entities

If the groups themselves are trackable entities (like "Eastern Special Project Team"), they can have their own attributes and slow change history. You might even consider making the group a dimension table with multi-valued attributes for members. See the Multi-Valued Attributes section!

Multi-Valued Attributes

We've covered when facts need to relate to multiple dimension rows. Now let's tackle when dimension rows need multiple values for an attribute.

Common Examples of Multi-Valued Attributes

  • Customers have multiple phone numbers
  • Bank accounts have multiple account holders
  • Students have multiple guardians
  • Patients have multiple medical conditions
  • Companies operate in multiple industries

Option 1: Simplifying (Flattening) the Attribute

The first option is to create multiple columns for the repeating attribute – this is called "flattening."

CUSTOMER

When Flattening Works Well

This approach is best when:

  • A limited number of values is acceptable
  • Each version has an easily identifiable role (home phone, office phone, mobile phone)
  • You won't need to filter or group by values that could appear in any column
Shortcomings of Flattening for Industries
  • Limited to fixed values – What if a customer needs 4 industries?
  • Complex filtering – Finding all "Manufacturing" customers requires checking industry_1, industry_2, AND industry_3
  • Grouping nightmare – Summarizing facts by industry is extremely difficult

Option 2: Using an Attribute Bridge

Just like dimension bridges, an attribute bridge can model multi-valued attributes. The bridge sits between the dimension and an outrigger.

How an Attribute Bridge Works

  1. Place multi-valued attributes in a separate outrigger table with its own surrogate key
  2. Create a bridge table with a group_key and a reference to the outrigger
  3. When a dimension row has a specific combination of values, create a group in the bridge
  4. The dimension references the group_key; join dimension → bridge → outrigger

Double-Counting with Attribute Bridges

The same double-counting risk exists! When you join fact → dimension → bridge → outrigger, facts get multiplied.

SELECT 
  customer.customer_name, 
  industry.industry_name 
FROM 
  customer, industry_group, industry 
WHERE 
  customer.industry_group_key = industry_group.industry_group_key AND 
  industry_group.industry_key = industry.industry_key;

-- Result:
-- Company C    Manufacturing
-- Company C    Services

Now add the fact table:

SELECT 
  customer.customer_name, 
  industry.industry_name, 
  SUM(order_dollars) 
FROM 
  order_facts, customer, industry_group, industry 
WHERE 
  order_facts.customer_key = customer.customer_key AND 
  customer.industry_group_key = industry_group.industry_group_key AND 
  industry_group.industry_key = industry.industry_key 
GROUP BY 
  customer_name, industry_name

-- Result:
-- Company C    Manufacturing    10,000
-- Company C    Services         10,000  ← SAME ORDER COUNTED TWICE!

Using Primary Member to Hide the Bridge

Notice the primary_industry flag in the bridge table. Filter by this flag to guarantee a single match per customer:

WHERE 
  ... 
  AND industry_group.primary_industry = 'Primary'
Hide the Bridge

Create a view that only shows the primary industry. End users work with this safe view. Only trained analysts get full access to produce impact reports.

Impact of Changes

Attribute bridges require careful attention to changes in source data. Type 2 changes create ripple effects!

Changes to the Outrigger

Change Type What Happens
Type 1 Simply update the outrigger. No big deal. ✓
Type 2 If "Services" → "Financial Services":
• New row in outrigger with new key
• New version of Company C must be created
• New group in bridge for "Financial Services" + "Manufacturing"

Changes to Group Membership

If Company C leaves "Services" and enters "Insurance":

  • Type 1: Update customer's industry_group_key to point to a new (or existing) group for "Manufacturing" + "Insurance"
  • Type 2: Create new row in customer table with new surrogate key, pointing to the new group. Old facts stay linked to old industry mix!
Key Insight

The group in the bridge/outrigger is a characteristic of the dimension. If the group changes, the thing the dimension represents has changed!

Changes to the Dimension

If Company C undergoes a Type 2 change (new surrogate key) but stays in the same industries, the new row can reuse the same group_key. The multi-valued attributes haven't changed!

Other Impacts of Attribute Bridges

When the Outrigger IS a Group

Things get confusing when the multi-valued attribute is itself a "group" (like employee committees, unions, etc.). The bridge then associates employees with groups they belong to.

Terminology Tip

When the outrigger represents real-world groups, don't use "group" to describe the bridge table. Call it an "association table" or "membership table" to avoid confusion!

Folding the Outrigger into the Bridge

If there are only one or two multi-valued attributes, you can eliminate the outrigger entirely by placing its columns directly in the bridge table. Industry_code and industry_name would appear in the industry_group table itself.

  • Fewer tables and joins
  • Industry names stored redundantly
  • Must ensure names are consistent across rows

Bridge as Fact Table

Because bridge tables consist primarily of foreign keys, they strongly resemble fact tables. Many BI tools will identify them as such!

Bridge ≈ Factless Fact Table

A bridge contains multiple key references – just like a fact table. Any allocation factors or flags might be identified as degenerate dimensions. This is fine semantically, but has one important implication:

Exception to the "No Fact Table Joins" Rule

Earlier chapters warned: never join two fact tables – it causes Cartesian products and double-counting.

But bridge tables exploit this Cartesian effect intentionally! If your tool treats the bridge as a fact table, you must make an exception to the no-join rule. When one "fact table" is actually a bridge, the join is essential and the Cartesian product is intended.

Related Reading

Factless fact tables are fully explored in Chapter 12. The concept of a table that captures relationships between dimensions without containing measures is perfectly valid!

Summary

Key Takeaways

  • Multi-valued dimensions occur when a fact must refer to more than one instance of a dimension. You can simplify into multiple one-to-many relationships, or use a bridge table.
  • Simplification works for a fixed number of relationships but makes some reporting difficult and doesn't scale.
  • Bridge tables allow facts to associate with any number of dimension rows, keeping reporting simple – but they introduce double-counting risk.
  • Control access carefully! Hide bridges from inexperienced users. Supplement with a primary member for safe, simplified analysis.
  • Allocation factors can prevent double-counting, but must be approved by business users and don't work for all fact types.
  • Many-to-many relationships can be resolved with an intersect table if your tools require it (even if it creates silly one-column tables).
  • Slow changes with bridges require careful planning. Type 2 changes create ripple effects across dimension rows, bridge tables, and groups.
  • Attribute bridges work the same way but sit between a dimension and an outrigger.
  • Tools may identify bridges as fact tables – that's fine, but make sure they don't inadvertently "drill across" when joining.

"The presence of a bridge makes it necessary to think carefully about the implications of slow changes, not only to attributes but also to relationships."

— Christopher Adamson
