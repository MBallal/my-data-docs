Understanding Recursive Hierarchies

In the world of data modeling, we often encounter hierarchies that follow predictable patterns—like Day → Month → Quarter → Year in a date dimension. These are called attribute hierarchies, and they're straightforward to model because each level is a distinct attribute.

But what happens when the hierarchy is more organic? Consider an organization chart where every person is an employee, yet some employees report to other employees who report to others. This is a recursive hierarchy—a structure where entities of the same type relate to one another in a parent-child pattern.

Key Concept: Recursive vs. Attribute Hierarchies

Attribute Hierarchy: Each level is a different attribute (e.g., City → State → Country). Easy to model as separate columns.

Recursive Hierarchy: All levels are the same entity type relating to itself (e.g., Employee → Manager → VP). Requires special modeling techniques.

Real-World Examples of Recursive Hierarchies

  • Organizational structures — Employees reporting to managers
  • Geographic territories — Sales regions containing sub-regions
  • Bill of Materials — Assemblies containing sub-assemblies
  • Account hierarchies — Parent accounts with child accounts
  • Category trees — Product categories with subcategories

The Reporting Challenge

Recursive hierarchies create unique reporting challenges that don't exist with simple attribute hierarchies. Business users typically want to do two things:

Looking Up the Hierarchy

"For this employee, who are all their managers up the chain?" This means traversing from a child node to all its ancestors. For example, finding all the managers above a specific salesperson, all the way up to the CEO.

Looking Down the Hierarchy

"For this manager, who are all the people underneath them?" This means traversing from a parent node to all its descendants. For example, finding all employees who ultimately report to a regional VP, whether directly or indirectly.

The SQL Limitation

Standard SQL wasn't designed for recursive traversal. While some databases support recursive CTEs (Common Table Expressions), these can be slow and aren't universally supported by all BI tools. We need modeling solutions that work within standard SQL constraints.

Figure 10.1: A Typical Organizational Hierarchy

An organizational hierarchy where each level contains the same entity type (Employee), creating a recursive relationship.

In this chapter, we'll explore two primary solutions for handling recursive hierarchies in dimensional models:

  1. Flattening the Hierarchy — Converting the recursive structure into fixed attribute columns
  2. Using a Bridge Table — Creating a separate table that pre-computes all hierarchical relationships

Each approach has trade-offs, and understanding when to use which technique is crucial for building effective data warehouse solutions.

Flattening a Recursive Hierarchy

The simplest solution to handle recursive hierarchies is to "flatten" them—transforming the recursive relationship into fixed columns within the dimension table. Instead of having a self-referential foreign key, you create explicit columns for each level of the hierarchy.

How Flattening Works

Consider an employee dimension. Instead of storing just an employee and their manager's ID, you store all levels explicitly:

Figure 10.2: Flattened Employee Dimension

A flattened dimension stores each hierarchy level as a separate attribute column.

Sample Data

Here's what the flattened data might look like:

employee_key employee_name level_1 level_2 level_3 level_4
1 John Smith John Smith - - -
2 Mary Johnson John Smith Mary Johnson - -
3 Bob Williams John Smith Mary Johnson Bob Williams -
4 Alice Davis John Smith Mary Johnson Bob Williams Alice Davis

Querying a Flattened Hierarchy

The beauty of flattening is that queries become trivially simple. No recursive logic or complex joins are needed: 

-- Find all sales for employees under Mary Johnson (VP Sales)
SELECT 
    e.employee_name,
    SUM(f.sales_amount) AS total_sales
FROM fact_sales f
JOIN dim_employee e ON f.employee_key = e.employee_key
WHERE e.level_2_name = 'Mary Johnson'
GROUP BY e.employee_name;

Senior Architect's Advice

Flattening is your "default" choice when the hierarchy has a fixed, predictable depth (usually 5-7 levels or fewer), doesn't change its structure frequently, and your business users primarily need to filter or group at specific levels. Don't over-engineer with bridge tables if flattening will do the job!

Handling Ragged Hierarchies

Real-world hierarchies are often "ragged"—meaning not all branches have the same depth. Some employees might report directly to the CEO, while others are five levels deep. When flattening a ragged hierarchy, you have two options:

Option 1: Use NULL or Placeholder Values

Leave higher-level columns NULL or use a placeholder like "N/A" for employees who don't have that many levels above them. This preserves the true structure but requires careful handling in queries. 

-- Handle NULLs in grouping
SELECT 
    COALESCE(level_3_name, level_2_name, level_1_name) AS manager,
    SUM(sales_amount) AS total_sales
FROM fact_sales f
JOIN dim_employee e ON f.employee_key = e.employee_key
GROUP BY 1;
Option 2: Repeat the Lowest Level

"Push down" the values so that every row has all levels populated. If someone reports to Level 2, repeat Level 2's value in Levels 3, 4, and 5. This makes aggregation easier but can be misleading if users don't understand the convention.

employee_name level_1 level_2 level_3
CEO CEO CEO CEO
VP Sales CEO VP Sales VP Sales
Sales Rep CEO VP Sales Sales Rep

When Flattening Works Best

Scenario Flattening Notes
Fixed depth (≤7 levels) ✓ Excellent Ideal use case
Stable structure ✓ Excellent Fewer ETL headaches
Simple reporting needs ✓ Excellent Queries are simple
Variable/deep hierarchy ✗ Poor Too many columns
Frequent restructuring ✗ Poor High maintenance cost
Ad-hoc level navigation ✗ Poor Can't traverse flexibly

Limitations of Flattening

Flattening struggles when: (1) you don't know how deep the hierarchy will go, (2) different branches have wildly different depths, (3) the hierarchy structure changes frequently, or (4) users need to navigate up/down flexibly rather than filtering at fixed levels. For these cases, you need a bridge table.

The Hierarchy Bridge Table

When flattening isn't enough, we turn to a more powerful technique: the hierarchy bridge table. This design pre-computes all the relationships in the hierarchy, allowing flexible navigation both up and down.

What is a Bridge Table?

A bridge table is an associative table that sits between a dimension and a fact table (or between a dimension and itself). For recursive hierarchies, it stores every ancestor-descendant pair in the hierarchy, along with metadata about their relationship.

Bridge Table Structure

The hierarchy bridge table contains one row for every pair of related nodes in the hierarchy. This includes direct parent-child relationships AND indirect relationships (grandparent to grandchild, etc.).

Figure 10.3: Hierarchy Bridge Table Design

The bridge table creates a many-to-many relationship between the employee dimension and itself, enabling flexible hierarchy navigation.

Understanding Bridge Table Contents

Let's see what data goes into the bridge table. Consider this simple three-level hierarchy:

Example Hierarchy

The bridge table for this hierarchy would contain:

ancestor_key descendant_key depth top_flag bottom_flag Explanation
1 1 0 Y N CEO to self
2 2 0 N N VP to self
3 3 0 N Y VP to self (leaf)
4 4 0 N Y Mgr to self (leaf)
1 2 1 Y N CEO → VP (direct)
1 3 1 Y Y CEO → VP (direct)
2 4 1 N Y VP → Mgr (direct)
1 4 2 Y Y CEO → Mgr (indirect)

Understanding the Columns

depth = 0: Self-referencing rows (every node relates to itself)
depth = 1: Direct parent-child relationships
depth > 1: Indirect relationships (grandparent, great-grandparent, etc.)
top_flag: 'Y' if the ancestor is at the top of the hierarchy
bottom_flag: 'Y' if the descendant is a leaf node (no children)

Using the Bridge: Looking Down

"Looking down" means finding all descendants of a given node—like asking "who are all the people under this manager?" 

-- Find all sales for employees under the CEO (key=1)
-- This includes all levels: direct reports AND their reports
SELECT 
    emp.employee_name,
    SUM(f.sales_amount) AS total_sales
FROM fact_sales f
JOIN dim_employee emp 
    ON f.employee_key = emp.employee_key
JOIN bridge_employee_hierarchy b 
    ON emp.employee_key = b.descendant_key
WHERE b.ancestor_key = 1  -- CEO's key
  AND b.bottom_flag = 'Y'  -- Only leaf employees (avoid double-counting)
GROUP BY emp.employee_name;

Using the Bridge: Looking Up

"Looking up" means finding all ancestors of a given node—like asking "who are all the managers above this employee?" 

-- Find all managers above a specific employee (key=4)
SELECT 
    ancestor.employee_name AS manager_name,
    b.depth AS levels_above
FROM bridge_employee_hierarchy b
JOIN dim_employee ancestor 
    ON b.ancestor_key = ancestor.employee_key
WHERE b.descendant_key = 4  -- The employee we're looking up from
  AND b.depth > 0  -- Exclude self-reference
ORDER BY b.depth;

Query Results Explained

For employee with key=4 (the Manager), this query would return:

manager_name levels_above
VP (Key 2) 1
CEO (Key 1) 2

The Double-Counting Problem

Here's where things get tricky. The bridge table's power—storing multiple paths—can also be its Achilles' heel. When aggregating facts through a bridge table, you can easily count the same data multiple times.

Critical Warning: Double-Counting

Because the bridge table contains rows for direct AND indirect relationships, a single fact row can be joined to multiple hierarchy paths. If you're not careful, sales for a bottom-level employee will be counted once for their manager, once for their director, once for their VP, and once for the CEO!

How Double-Counting Happens

Figure 10.4: The Double-Counting Problem

The $1,000 sale gets counted multiple times because it joins to both the VP's path and the direct CEO path in the bridge table.

Avoiding Double-Counting

The solution is to only count facts at the leaf level of the hierarchy. This is why we include the bottom_flag column in our bridge table.

The Golden Rule

When aggregating facts through a hierarchy bridge, always filter to bottom_flag = 'Y'. This ensures each fact is counted exactly once, at the lowest level where it actually occurred. 

-- CORRECT: Only count leaf-level facts
SELECT 
    ancestor.employee_name,
    SUM(f.sales_amount) AS total_sales
FROM fact_sales f
JOIN bridge_employee_hierarchy b 
    ON f.employee_key = b.descendant_key
JOIN dim_employee ancestor 
    ON b.ancestor_key = ancestor.employee_key
WHERE b.bottom_flag = 'Y'  -- KEY: Only leaf nodes!
GROUP BY ancestor.employee_name;

Alternative: Use a Weighting Factor

Some designs add a weight_factor column to the bridge table. For simple hierarchies, leaf-level relationships get a weight of 1.0, and non-leaf relationships get a weight of 0.0. This allows queries to use SUM(amount * weight_factor) instead of filtering.

Approach Pros Cons
Filter on bottom_flag Simple, intuitive Requires WHERE clause
Weight factor Works with any aggregation More complex ETL, can be confusing

Hiding the Bridge from Novice Users

Bridge tables add complexity. While a skilled analyst can write the necessary SQL, what about business users using BI tools? The solution is to create views that hide the bridge table complexity.

Creating User-Friendly Views

You can create views that pre-join the bridge table with appropriate filters, presenting a simpler interface to users: 

-- View for "looking down" queries
CREATE VIEW vw_employee_with_descendants AS
SELECT 
    ancestor.employee_key AS manager_key,
    ancestor.employee_name AS manager_name,
    descendant.employee_key,
    descendant.employee_name,
    b.depth,
    b.bottom_flag
FROM dim_employee ancestor
JOIN bridge_employee_hierarchy b 
    ON ancestor.employee_key = b.ancestor_key
JOIN dim_employee descendant 
    ON b.descendant_key = descendant.employee_key;
-- Simplified view for leaf-level aggregation
CREATE VIEW vw_manager_to_leaf_employees AS
SELECT 
    ancestor.employee_key AS manager_key,
    ancestor.employee_name AS manager_name,
    descendant.employee_key,
    descendant.employee_name
FROM dim_employee ancestor
JOIN bridge_employee_hierarchy b 
    ON ancestor.employee_key = b.ancestor_key
JOIN dim_employee descendant 
    ON b.descendant_key = descendant.employee_key
WHERE b.bottom_flag = 'Y';  -- Pre-filtered to prevent double-counting

Senior Architect's Advice

Always provide pre-built views for your BI tools and end users. Document which view to use for what purpose. The raw bridge table should be for advanced analysts only. Consider naming conventions like vw_safe_* for views that prevent double-counting.

Resolving the Many-to-Many Relationship

Some BI tools struggle with many-to-many relationships that bridge tables create. You may need to:

  • Configure the BI tool's semantic layer to understand the bridge pattern
  • Create separate "role-playing" dimension views (one as ancestor, one as descendant)
  • Build OLAP cubes that pre-aggregate through the hierarchy
  • Use the BI tool's hierarchy features if they support recursive structures

Changes and the Hierarchy Bridge

Real-world hierarchies change. People get promoted, departments merge, reporting lines shift. How you handle these changes in your bridge table depends on whether you're doing Type 1 or Type 2 slowly changing dimensions.

Type 1 Changes: Overwrite History

With Type 1 changes, you simply update the hierarchy to reflect the current state. Historical analysis will show everyone in their current position, even for past time periods.

Type 1 Scenario

Alice was promoted from Manager to Director yesterday. With Type 1:

  • Update Alice's position in dim_employee
  • Rebuild the bridge table to reflect new relationships
  • Historical sales now roll up through her new position

The Ripple Effect

Type 1 changes in a hierarchy can cause a ripple effect. When Alice moves, every relationship involving her must be recalculated—her relationships with her new manager, her old subordinates' paths to the top, etc. This can require regenerating large portions of the bridge table.

Type 2 Changes: Preserve History

Type 2 changes create new records to track historical states. This is more complex but allows accurate historical analysis.

Figure 10.5: Type 2 Bridge Table with Effective Dates

Adding effective_date and expiration_date columns enables point-in-time hierarchy queries. 

-- Query sales using hierarchy as it was on a specific date
SELECT 
    ancestor.employee_name,
    SUM(f.sales_amount) AS total_sales
FROM fact_sales f
JOIN dim_date d ON f.date_key = d.date_key
JOIN bridge_employee_hierarchy b 
    ON f.employee_key = b.descendant_key
    AND d.full_date BETWEEN b.effective_date AND b.expiration_date
JOIN dim_employee ancestor 
    ON b.ancestor_key = ancestor.employee_key
WHERE b.bottom_flag = 'Y'
GROUP BY ancestor.employee_name;

ETL Considerations

Initial Load

When first populating the bridge table, you need to:

  1. Load the base dimension with parent references
  2. Use recursive logic (recursive CTE or iterative process) to traverse all paths
  3. For each node, generate rows connecting it to all ancestors at all depths
  4. Calculate flags (top_flag, bottom_flag) based on hierarchy position
Incremental Updates

For ongoing changes, you typically:

  1. Identify changed nodes (new, moved, or deleted)
  2. For Type 1: Delete and regenerate affected paths
  3. For Type 2: Expire old records and create new ones
  4. Remember the ripple effect—one change may affect many bridge rows

Many teams opt to completely rebuild the bridge table nightly rather than doing complex incremental logic, especially for Type 1 designs.

Variations on the Hierarchy Bridge

The basic bridge pattern can be extended to handle more complex scenarios you'll encounter in the real world.

Multiple Parents (Network Structures)

Sometimes entities belong to multiple hierarchies or have multiple parents. For example:

  • A project reports to both a business sponsor and a technical lead
  • A product belongs to multiple category trees (by function AND by brand)
  • An employee works on multiple teams

Handling Multiple Parents

The bridge table naturally supports multiple parents—just add more rows! If Product A belongs to both Category X and Category Y, create bridge rows connecting it to both paths. However, be extra careful about double-counting in this scenario.

Multiple Hierarchy Types

Sometimes the same entity participates in different types of hierarchies. For example, employees might be in:

  • An organizational hierarchy (who reports to whom)
  • A geographic hierarchy (where they're located)
  • A skill hierarchy (their competency group)

You can handle this by adding a hierarchy_type column to the bridge table: 

CREATE TABLE bridge_employee_hierarchy (
    hierarchy_type      VARCHAR(50),  -- 'ORG', 'GEO', 'SKILL'
    ancestor_key        INT,
    descendant_key      INT,
    depth               INT,
    top_flag            CHAR(1),
    bottom_flag         CHAR(1),
    PRIMARY KEY (hierarchy_type, ancestor_key, descendant_key)
);

Partial Hierarchy Deployment

For very large or deep hierarchies, you might not need the full bridge. Consider:

  • Depth-limited bridges: Only store relationships up to N levels deep
  • Selective bridging: Only build bridges for certain branches
  • On-demand calculation: Use recursive CTEs for rare queries, bridge for common ones

Combining Flattening and Bridging

Senior Architect's Advice

You don't have to choose just one approach! A common pattern is to:

1. Flatten the top levels (e.g., CEO → VP → Director) for common rollup reports
2. Use a bridge for flexible navigation in the lower levels

This gives you the simplicity of flattening where it works, with the flexibility of bridging where it's needed.

Chapter Summary

Recursive hierarchies are a challenging but common pattern in data warehousing. Here's what you need to remember:

🔄 Recursive Hierarchies

Structures where entities of the same type relate to each other in parent-child relationships. Common in org charts, bills of materials, and category trees.

📊 Flattening

The simpler approach: convert hierarchy levels to fixed columns. Best for stable, shallow hierarchies with predictable depth.

🌉 Bridge Tables

Store all ancestor-descendant pairs with depth. Enables flexible "look up" and "look down" queries. Required for complex or variable hierarchies.

⚠️ Double-Counting

The critical trap! Always filter on bottom_flag when aggregating facts through a bridge to count each fact exactly once.

👥 User Experience

Create views to hide bridge complexity from end users. Configure BI tools appropriately for many-to-many relationships.

🔄 Managing Change

Type 1 overwrites (simpler ETL, no history). Type 2 preserves history (complex ETL, accurate historical analysis).

Decision Framework

Scenario Recommended Approach
Fixed depth ≤5 levels, stable structure Flatten the hierarchy
Variable/unknown depth Use Bridge Table
Need flexible up/down navigation Use Bridge Table
Simple level-based reporting only Flatten the hierarchy
Multiple parents/hierarchies Use Bridge Table with type column
Need historical accuracy Type 2 Bridge with effective dates
Simple ETL, current view only Type 1 (flatten or bridge)

Final Thoughts

As a senior architect, I always tell junior modelers: start with flattening. It's simpler to implement, easier to query, and works for most business needs. Only move to a bridge table when you have a clear requirement that flattening can't meet—like variable depth, multiple parents, or true hierarchical navigation needs. When you do use a bridge, always protect your users from double-counting by providing pre-filtered views and clear documentation.
