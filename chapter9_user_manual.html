1. Introduction: When Simple Relationships Aren't Enough

Welcome to one of the most challenging—but also most powerful—topics in dimensional modeling. Until now, you may have learned that every star schema follows a simple pattern: each fact (like a sale or an order) relates to exactly one value in each dimension (like one product, one customer, one date). This creates the familiar "star" shape that gives star schemas their name.

But real life isn't always that simple. Sometimes, the data you need to model doesn't fit neatly into this one-to-one pattern. This chapter tackles two specific challenges:

Challenge 1: Multi-Valued Dimensions

This occurs when a single fact (like an order) needs to be associated with multiple values from a dimension table. For example, what if an order is handled by two salespeople working together? The order doesn't belong to just one salesperson—it belongs to both.

Challenge 2: Multi-Valued Attributes

This occurs when a single row in a dimension table needs to store multiple values for the same attribute. For example, what if a customer company operates in multiple industries? You can't just put "Manufacturing" in the industry column—the company is also in "Services."

The solution to both challenges involves a special type of table called a bridge table. Think of a bridge table like a real bridge connecting two places that couldn't otherwise be directly connected. It's incredibly powerful, but it also comes with risks that you must understand.

The Double-Edged Sword

A bridge table provides ultimate flexibility—you can capture any number of relationships and answer complex analytical questions. However, if used incorrectly, it can lead to double-counting: counting the same fact multiple times, which gives completely wrong results. Many organizations refuse to use bridge tables because of this risk. This chapter will teach you both the power and the pitfalls so you can make informed decisions.

2. Understanding Standard One-to-Many Relationships

What Is a One-to-Many Relationship?

Before diving into the complex scenarios, let's make sure you fully understand how relationships normally work in a star schema. This foundation will help you understand why the challenges in this chapter are... well, challenging.

Key Concept: One-to-Many Relationship

In a one-to-many relationship, one row in a parent table (like a dimension) can be related to many rows in a child table (like a fact table), but each row in the child table relates to exactly one row in the parent table.

Real-World Analogy

Think of a mother and her children. One mother can have many children (one-to-many), but each child has exactly one biological mother. In database terms:

  • The mother is like a dimension table row
  • Each child is like a fact table row
  • One mother → many children (but each child → exactly one mother)

In a star schema, this means:

  • A single product can appear in many order_facts rows
  • But each order_facts row refers to exactly one product
  • This is true for every dimension: day, customer, salesperson, etc.

Figure 9-1: Standard One-to-Many Relationships

┌─────────────┐ ┌─────────────┐ │ DAY │ │ PRODUCT │ │─────────────│ │─────────────│ │ day_key │────┐ ┌────│ product_key │ │ date │ │ │ │ product_name│ │ month │ │ │ │ brand_name │ └─────────────┘ │ │ └─────────────┘ │ │ ▼ ▼ ┌─────────────────────────┐ │ ORDER_FACTS │ │─────────────────────────│ │ day_key (FK) │ │ product_key (FK) │ │ customer_key (FK) │ │ salesrep_key (FK) │ │ order_dollars │ └─────────────────────────┘ ▲ ▲ │ │ ┌─────────────┐ │ │ ┌─────────────┐ │ CUSTOMER │────┘ └────│ SALESREP │ │─────────────│ │─────────────│ │ customer_key│ │ salesrep_key│ │ cust_name │ │ salesrep_nm │ └─────────────┘ └─────────────┘ The arrows with a fork (▼) point toward the "many" side. Each dimension has a one-to-many relationship with the fact table.

Each dimension table (DAY, PRODUCT, CUSTOMER, SALESREP) connects to the ORDER_FACTS table through a foreign key. Each fact row refers to exactly one row in each dimension.

Why This Matters for Your Queries

The one-to-many relationship is essential because it allows your SQL queries to work correctly. Consider this typical query that calculates total order dollars by brand: 

SELECT 
    product.brand_name, 
    SUM(order_facts.order_dollars) AS total_sales
FROM 
    product, order_facts 
WHERE 
    product.product_key = order_facts.product_key 
GROUP BY 
    product.brand_name

This query works perfectly because each order is associated with exactly one product, and therefore exactly one brand_name. The database can confidently group orders by brand without any confusion or overcounting.

Why This Is Important

The entire query pattern you've learned—selecting dimensions and using them to aggregate facts—relies on this one-to-many relationship. When we break this pattern (as we'll do in this chapter), things get complicated quickly.

But what happens when reality breaks this pattern? What if an order is handled by two salespeople working as a team? The diagram below shows this problem:

When multiple salespeople collaborate on an order, the simple star schema breaks down. The fact table can't hold multiple foreign keys to the salesrep table.

3. Multi-Valued Dimensions

The Problem Explained

A multi-valued dimension occurs when a fact table row may need to refer to more than one row in a dimension table. In our example, a single order might be credited to two, three, or even more salespeople who worked together.

Definition: Multi-Valued Dimension

A multi-valued dimension is a dimension that can take on multiple values with respect to a single fact. Instead of a one-to-many relationship, you have a many-to-many relationship: one fact can relate to many dimension rows, and one dimension row can relate to many facts.

There are two main approaches to solving this problem:

  1. Simplify the relationship by creating multiple columns in the fact table
  2. Use a bridge table to connect facts to any number of dimension rows

Let's explore both solutions in detail.

Solution 1: Simplifying the Relationship

The simplest approach is to "flatten" the many-to-many relationship by creating multiple one-to-many relationships. Instead of having one salesrep_key column in the fact table, you create two (or more): primary_salesrep_key and secondary_salesrep_key.

Figure 9-3: Simplifying with Primary and Secondary Salespeople

┌─────────────────────────────────────────┐ │ ORDER_FACTS │ │─────────────────────────────────────────│ │ day_key │ │ product_key │ │ customer_key │ │ primary_salesrep_key ──────┐ │ │ secondary_salesrep_key ────┼────┐ │ │ order_dollars │ │ │ └────────────────────────────┼────┼───────┘ │ │ ▼ ▼ ┌────────────────────────────┐ │ SALESREP │ │────────────────────────────│ │ salesrep_key │ │ salesperson_name │ │ region │ └────────────────────────────┘ When only one salesperson is involved, the secondary_salesrep_key refers to a special "Not Applicable" row in the salesrep table.

The fact table now has two foreign keys pointing to the salesrep table. Each plays a different "role" (primary vs. secondary).

Advantages of This Approach:

  • Simple to understand and implement
  • Uses familiar star schema patterns
  • No risk of double-counting when querying the primary salesperson

Disadvantages of This Approach:

  • Limited to a fixed number: What if three salespeople collaborate? You'd need to add a third column. Four? A fourth column. This quickly becomes unmanageable.
  • Reporting is difficult: If you want to see all orders that Ann worked on (regardless of whether she was primary or secondary), you need complex queries that check both columns.
  • Grouping is messy: Counting total sales per salesperson requires summing separate queries for primary and secondary roles.

Reporting Challenge Example

To count all sales for salesperson Ann Davis (whether primary or secondary), you'd need a query like this—notice how complicated it becomes: 

SELECT SUM(order_dollars)
FROM order_facts
WHERE 
    primary_salesrep_key = (Ann's key)
    OR secondary_salesrep_key = (Ann's key)

And if there were three roles, you'd need to check three columns. This gets tedious and error-prone quickly.

Solution 2: The Dimension Bridge Table

A more flexible solution uses a bridge table to connect facts to any number of dimension rows. The bridge table sits "between" the fact table and the dimension table, acting as an intermediary.

Key Concept: The Bridge Table

A bridge table creates groups of dimension members. Instead of the fact table pointing directly to salespeople, it points to a "group" of salespeople. That group can have one member, two members, or any number.

Here's how it works:

  1. Create a sales_group bridge table with two columns: sales_group_key and salesrep_key
  2. When Ann and Henry collaborate on an order, create a group (say, group #1) with two rows in the bridge table—one for Ann, one for Henry
  3. The order in the fact table references this group (group #1), not individual salespeople
  4. To find salespeople for an order, join the fact table → bridge table → salesrep table

Figure 9-4: The Bridge Table Solution

┌─────────────┐ ┌─────────────┐ ┌─────────────┐ │ DAY │ │ PRODUCT │ │ CUSTOMER │ └──────┬──────┘ └──────┬──────┘ └──────┬──────┘ │ │ │ ▼ ▼ ▼ ├────────────────┼────────────────┤ │ │ │ ┌─────────────────────┐ │ └────►│ ORDER_FACTS │◄────┘ │─────────────────────│ │ day_key │ │ product_key │ │ customer_key │ │ sales_group_key ────┼──────┐ │ order_dollars │ │ └─────────────────────┘ │ │ ▼ ┌───────────────────┐ │ SALES_GROUP │ ◄── Bridge Table │───────────────────│ │ sales_group_key │ │ salesrep_key │ └─────────┬─────────┘ │ ▼ ┌───────────────────┐ │ SALESREP │ │───────────────────│ │ salesrep_key │ │ salesperson_name │ │ region │ └───────────────────┘ ═══════════════════════════════════════════════════════════════ EXAMPLE DATA: ORDER_FACTS SALES_GROUP SALESREP ─────────────────────── ───────────────── ────────────────────── day_key | ... | group_key group_key | rep_key rep_key | name ─────────────────────── ───────────────── ────────────────────── 2012 | ... | 1 1 | 222 222 | Ann Davis 1 | 333 333 | Henry Perez ─────────────────────── ───────────────── ────────────────────── Group #1 contains both Ann (222) and Henry (333). The order references Group #1, linking it to both salespeople. ═══════════════════════════════════════════════════════════════

The bridge table (SALES_GROUP) connects the fact table to any number of salespeople by creating groups. The example shows Ann and Henry sharing credit for a $1,000 order.

Advantages of the Bridge Table:

  • Unlimited flexibility: Groups can have any number of members
  • Easy reporting: To find all sales involving Ann, simply join through the bridge table—no need to check multiple columns
  • Clean queries: The same query pattern works regardless of group size

ETL Implications

The ETL (Extract, Transform, Load) process must manage these groups. When loading a new order, the process must either find an existing group with the same members or create a new group. If Ann and Henry collaborate again, the same group can be reused.

Understanding Double-Counting

Here's the dangerous downside of bridge tables: they make it very easy to count the same fact multiple times, giving you completely wrong results.

Critical Warning: Double-Counting

When you join the fact table through a bridge to a dimension, each fact can appear multiple times in your result—once for each member of the group. If you're not careful, you'll count the same order twice, three times, or more!

Let's see this in action. Ann and Henry's $1,000 order is linked to a group containing both of them. If you query orders by region: 

SELECT 
    salesrep.region, 
    SUM(order_facts.order_dollars) AS total
FROM 
    salesrep, sales_group, order_facts 
WHERE 
    order_facts.sales_group_key = sales_group.sales_group_key 
    AND sales_group.salesrep_key = salesrep.salesrep_key 
GROUP BY 
    salesrep.region

The problem: Both Ann and Henry are in the "East" region. The database will match the $1,000 order to Ann (region = East), and then match it again to Henry (also region = East). Result: the East region shows $2,000 instead of $1,000!

When Double-Counting Is Actually Wanted

Sometimes, this behavior is exactly what you want! Consider an impact report: "Show me the total order volume associated with each salesperson." In this case, you want the $1,000 order to count for both Ann and Henry—each of them genuinely participated in $1,000 worth of business.

The Grand Total Trap

Even when double-counting is appropriate for individual rows, never create a grand total from such a report! Ann's $1,000 + Henry's $1,000 does NOT mean the company made $2,000. It's the same order counted twice.

Safe Grouping Rule

The only safe way to construct an impact report is to group by a column that has a unique value for each group member—typically the natural key (like salesrep_id) or the surrogate key. Grouping by any other attribute (like region) risks double-counting when multiple group members share that attribute value.

Adding an Allocation Factor

One way to prevent double-counting is to add an allocation factor to the bridge table. This tells the database what percentage of each fact should be credited to each group member.

Figure 9-5: Bridge Table with Allocation Factor

SALES_GROUP (with allocation) SALESREP ─────────────────────────────── ────────────────────────── group_key | rep_key | allocation rep_key | name | region ─────────────────────────────── ────────────────────────── 1 | 222 | 0.75 222 | Ann Davis | East 1 | 333 | 0.25 333 | Henry Perez | East ─────────────────────────────── ────────────────────────── Ann gets 75% credit, Henry gets 25% credit. Query: SELECT salesperson_name, SUM(order_dollars * allocation) FROM salesrep, sales_group, order_facts WHERE [join conditions] GROUP BY salesperson_name Result: ───────────────────────────────── salesperson_name | allocated_dollars ───────────────────────────────── Ann Davis | 750 Henry Perez | 250 ───────────────────────────────── Total: 750 + 250 = $1,000 ✓ (No double-counting!)

By multiplying each fact by its allocation factor before summing, you prevent double-counting. The allocated amounts correctly total to the original order value.

The catch: Allocation factors must come from the business, not from the technical team. You need a legitimate business rule that defines how credit is split. If no such rule exists (which is common), you can't use this approach.

Non-Allocatable Facts

Some facts simply cannot be meaningfully allocated. If Ann and Henry sold one refrigerator, you can't say Ann sold 0.75 refrigerators! This may be acceptable for reporting purposes, but it can confuse users.

Supplementing with a Primary Member

A common best practice is to combine the bridge table with a simplified solution: add a direct primary_salesrep_key column to the fact table that points to one "main" salesperson. This gives you the best of both worlds:

  • For most users: Use the direct primary_salesrep_key for simple, safe reporting
  • For advanced analysts: Use the bridge table for complex impact reports

Figure 9-6: Bridge Supplemented with Primary Member

┌─────────────────────────┐ │ ORDER_FACTS │ │─────────────────────────│ │ day_key │ │ product_key │ │ customer_key │ │ sales_group_key ────────┼─────► SALES_GROUP (bridge) │ primary_salesrep_key ───┼─────► SALESREP (direct, safe) │ order_dollars │ └─────────────────────────┘ ┌─────────────────────────────────────────────────────────────────────┐ │ TWO PATHS TO SALESREP │ ├─────────────────────────────────────────────────────────────────────┤ │ │ │ PATH 1: Direct (Safe) │ │ ───────────────────── │ │ ORDER_FACTS.primary_salesrep_key → SALESREP │ │ • Always returns exactly one salesperson per order │ │ • NO risk of double-counting │ │ • Give this to regular report users │ │ │ │ PATH 2: Through Bridge (Powerful but Risky) │ │ ─────────────────────────────────────────── │ │ ORDER_FACTS → SALES_GROUP → SALESREP │ │ • Returns ALL salespeople involved in each order │ │ • RISK of double-counting │ │ • Only for trained analysts who understand the risks │ │ │ └─────────────────────────────────────────────────────────────────────┘

By providing two paths to the salesrep dimension, you can hide the risky bridge from casual users while still enabling sophisticated analysis when needed.

Best Practice

When implementing a bridge between a fact table and a dimension, always consider supplementing it with a direct relationship that isolates a primary role. Hide the bridge from most users, and only expose it to analysts who understand the risks.

Handling Slow Changes with Bridges

If you've learned about Slowly Changing Dimensions (SCDs), you know that dimension data can change over time. Bridge tables add complexity to slow change processing:

Type 1 Changes (Overwrite)

If a bridged dimension row undergoes a Type 1 change (simply updating the value), no special action is needed for the bridge. The salesperson remains associated with existing groups.

Type 2 Changes (Add New Row)

If a dimension row undergoes a Type 2 change (creating a new version with a new surrogate key), the next collaboration involving that person will require a new group. The old group references the old version; the new group will reference the new version.

Changes to Group Membership

If group membership itself is tracked as a meaningful entity (e.g., "Eastern Special Project Team"), changes to membership can also be handled as Type 1 or Type 2:

  • Type 1: Update the bridge table rows (delete/add members)
  • Type 2: Create a new group with new members, preserving the old group for historical facts

Resolving Many-to-Many for Software Tools

Some database modeling tools, BI software, or even the RDBMS itself may not accept many-to-many relationships. If your tools require each foreign key to reference a primary key, you can resolve this by creating an "intersect table":

Figure 9-7: Resolving the Many-to-Many Relationship

┌─────────────────────────┐ │ ORDER_FACTS │ │─────────────────────────│ │ sales_group_key ────────┼──────┐ │ order_dollars │ │ └─────────────────────────┘ │ ▼ ┌───────────────────┐ │ SALES_GROUP │ │───────────────────│ │ sales_group_key │ ◄── Only ONE column! └─────────┬─────────┘ (Just the key) │ ▼ ┌───────────────────┐ │ GROUP_MEMBERSHIP │ ◄── Intersect table │───────────────────│ │ sales_group_key │ │ salesrep_key │ └─────────┬─────────┘ │ ▼ ┌───────────────────┐ │ SALESREP │ └───────────────────┘ The SALES_GROUP table looks silly (just one column!) but it satisfies tools that require every foreign key to point to a primary key.

By adding a single-column table (SALES_GROUP), you create proper primary key-foreign key relationships that satisfy strict database tools.

4. Multi-Valued Attributes

The Problem Explained

Multi-valued attributes are different from multi-valued dimensions. This time, the problem isn't about facts relating to multiple dimension rows—it's about a single dimension row needing to store multiple values for one attribute.

Definition: Multi-Valued Attribute

A multi-valued attribute is a dimension attribute that can take on more than one value for a single dimension member. For example, a customer company might operate in multiple industries: "Manufacturing" and "Services."

Figure 9-8: The Multi-Valued Attribute Problem

┌───────────────────┐ │ CUSTOMER │ │───────────────────│ │ customer_key │ │ customer_id │ │ customer_name │ │ industry ?????? │◄── Problem: What goes here? └───────────────────┘ CUSTOMER DATA: ─────────────────────────────────────────────────────────── Customer | Industry ─────────────────────────────────────────────────────────── Company A | Manufacturing Company B | Services Company C | Manufacturing, Services ◄── TWO industries! Company D | Finance ─────────────────────────────────────────────────────────── How do we store Company C's industries? We can't put "Manufacturing, Services" in one column— we couldn't easily search or group by industry!

Some customers operate in multiple industries. A single "industry" column cannot properly represent this complexity.

Just like with multi-valued dimensions, we have two main solutions:

  1. Flatten the attribute into multiple columns
  2. Use an attribute bridge connecting to an outrigger table

Solution 1: Simplifying the Attribute

The simplest approach is to create multiple columns for the same attribute:

Figure 9-9: Flattening Multi-Valued Attributes

┌───────────────────────────┐ │ CUSTOMER │ │───────────────────────────│ │ customer_key │ │ customer_id │ │ customer_name │ │ industry_1 ───────────────│◄── First industry │ industry_2 ───────────────│◄── Second industry │ industry_3 ───────────────│◄── Third industry (if needed) └───────────────────────────┘ Company C would have: industry_1 = "Manufacturing" industry_2 = "Services" industry_3 = NULL or "N/A"

Problems with Flattening:

  • Limited to a fixed number: What if a company is in 5 industries? You'd need 5 columns.
  • Filtering is complex: To find all companies in "Services," you must check all three columns.
  • Grouping is very difficult: You can't easily produce a report showing total sales by industry when the industry might be in any of three columns.

When Flattening Works Well

Flattening is appropriate when:

  • A small, fixed number of values is acceptable
  • Each value has a distinct role (e.g., "home phone," "work phone," "mobile phone")
  • You won't need to filter or group by these values

Solution 2: The Attribute Bridge Table

An attribute bridge works similarly to a dimension bridge, but instead of connecting a fact table to a dimension, it connects a dimension table to an outrigger (a secondary table containing attribute values).

Key Concept: Attribute Bridge

An attribute bridge connects a dimension table to an outrigger table that holds the multi-valued attributes. The dimension row contains a "group key" that links to one or more rows in the bridge, which in turn links to the outrigger.

Figure 9-10: The Attribute Bridge Solution

┌─────────────────────┐ │ ORDER_FACTS │ │─────────────────────│ │ day_key │ │ customer_key ───────┼──────┐ │ product_key │ │ │ order_dollars │ │ └─────────────────────┘ │ ▼ ┌───────────────────────┐ │ CUSTOMER │ │───────────────────────│ │ customer_key │ │ customer_id │ │ customer_name │ │ industry_group_key ───┼──────┐ └───────────────────────┘ │ │ ▼ ┌─────────────────────────────┐ │ INDUSTRY_GROUP │ ◄── Bridge │─────────────────────────────│ │ industry_group_key │ │ industry_key │ │ primary_industry (flag) │ └──────────────┬──────────────┘ │ ▼ ┌─────────────────────────────┐ │ INDUSTRY │ ◄── Outrigger │─────────────────────────────│ │ industry_key │ │ industry_code │ │ industry_name │ └─────────────────────────────┘ ═══════════════════════════════════════════════════════════════════════════ EXAMPLE DATA: CUSTOMER INDUSTRY_GROUP INDUSTRY ───────────────────────────────── ──────────────────────── ──────────────── key | id | name | grp_key grp_key|ind_key|primary key |code |name ───────────────────────────────── ──────────────────────── ──────────────── 2012 | C771 | Company C | 100 100 | 901 | Yes 901| B404| Manufacturing 100 | 902 | No 902| B492| Services ───────────────────────────────── ──────────────────────── ──────────────── Company C is in industry group 100. Group 100 links to industries 901 (Manufacturing) and 902 (Services). Manufacturing is flagged as the "primary" industry. ═══════════════════════════════════════════════════════════════════════════

The attribute bridge (INDUSTRY_GROUP) connects the CUSTOMER dimension to the INDUSTRY outrigger, allowing each customer to be associated with multiple industries.

Advantages of the Attribute Bridge:

  • Unlimited values: A customer can be in any number of industries
  • Easy filtering: Join customer → bridge → industry, then filter on industry_name
  • Flexible reporting: Group facts by industry easily

Double-Counting with Attribute Bridges

Just like dimension bridges, attribute bridges introduce the risk of double-counting. When you join a fact table → dimension → bridge → outrigger, each fact can appear multiple times.

Consider this query involving Company C (which is in two industries):

SELECT 
    customer.customer_name, 
    industry.industry_name
FROM 
    customer, industry_group, industry 
WHERE 
    customer.industry_group_key = industry_group.industry_group_key 
    AND industry_group.industry_key = industry.industry_key

The result contains two rows for Company C:

CUSTOMER_NAME  | INDUSTRY_NAME
───────────────┼───────────────
Company C      | Manufacturing
Company C      | Services

Now imagine adding facts to this query. If Company C has a $10,000 order, it will appear twice—once for each industry. If you're building an industry impact report, this might be intentional. But if you're not careful, you'll end up with inflated totals.

Using a Primary Flag

Notice in Figure 9-10 that the bridge table has a primary_industry column. This flag identifies one industry as "primary" for each customer. You can use this flag to filter results for casual users, showing only the primary industry: 

SELECT 
    customer.customer_name, 
    industry.industry_name
FROM 
    customer, industry_group, industry 
WHERE 
    customer.industry_group_key = industry_group.industry_group_key 
    AND industry_group.industry_key = industry.industry_key
    AND industry_group.primary_industry = 'Yes'

This returns only one row per customer, eliminating the double-counting risk.

Impact of Changes

Attribute bridges require careful handling of changes. Here are the key scenarios:

Changes to the Outrigger (e.g., Industry Name)

  • Type 1: Simply update the outrigger. All customers linked to that industry see the change.
  • Type 2: Creates a ripple effect! A new industry row gets a new key. Every customer referencing the old industry needs a new version with a new group pointing to the new industry.

Changes to Group Membership (e.g., Customer Leaves an Industry)

  • Type 1: Update the customer's industry_group_key to point to a different group (or update the existing group's rows).
  • Type 2: Create a new customer row with a new group. The old customer row (with old industries) remains linked to historical facts.

Changes to the Dimension (e.g., Customer Name)

  • If industries haven't changed, the new customer row can reuse the same industry_group_key.
  • No need to modify the bridge or outrigger.

Important Note

The multi-valued attribute (industry) is conceptually part of the dimension (customer), even though it's physically stored in a bridge and outrigger. When group membership changes, it's like the dimension itself changed—and should be treated accordingly for SCD purposes.

5. Chapter Summary

This chapter has equipped you with tools to handle real-world complexity that doesn't fit the traditional one-to-many relationship between dimensions and facts. Here are the key takeaways:

Multi-Valued Dimensions

  • When a fact must relate to multiple dimension rows, you can simplify by using multiple foreign key columns—but this limits you to a fixed number and makes reporting difficult.
  • A bridge table allows a fact to associate with any number of dimension rows while keeping queries simple.
  • Bridge tables create a significant risk of double-counting—access must be carefully controlled.
  • Consider adding an allocation factor to the bridge, or supplementing with a primary member relationship for safe basic reporting.

Multi-Valued Attributes

  • When a dimension attribute needs multiple values, you can flatten into multiple columns—but this limits flexibility and complicates filtering/grouping.
  • An attribute bridge connects the dimension to an outrigger, allowing unlimited attribute values.
  • The same double-counting risks apply—use a primary flag to help protect casual users.

Handling Changes

  • Type 1 changes to bridged data are straightforward—just update in place.
  • Type 2 changes create ripple effects: new surrogate keys in one table may require new groups and new dimension rows.
  • The many-to-many relationship can be resolved with an intersect table if your software requires it.

Bridge Tables as Fact Tables

  • Some BI tools identify bridge tables as fact tables because they contain multiple foreign keys.
  • This is acceptable, but ensure the tool doesn't try to "drill across" between the bridge and other fact tables.

  • Concatenated Values: An alternative approach (not covered in this manual) concatenates multiple values into a single text attribute. This works with SQL substring functions but cannot be used for impact reports.
