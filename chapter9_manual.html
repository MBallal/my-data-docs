1. How to Use This Manual

Read this chapter-long guide from top to bottom if you are new to dimensional design. Each later section assumes you understand the vocabulary introduced earlier, but you can also jump to a section via the table of contents when you need a refresher.

  • If you are modeling: follow the decision flow (Sections 3–7) to pick between simplification and a bridge, then apply the change-management guidance (Sections 8 and 13).
  • If you are writing SQL or configuring BI tools: focus on the double-counting sections (6 and 12) and the tooling precautions (9 and 14.4).
  • If you lead ETL (Extract, Transform, Load) work: pay special attention to the group creation steps, allocation handling, and slow-change responses spelled out in Sections 5, 7, 8, and 13.

2. Why the Default Star Pattern Struggles Here

Chapter 9 sits in Part III (Dimension Design) and starts by revisiting the go-to reporting pattern for a star schema: choose dimensions, join them to the fact table, and let those dimensions control how facts are grouped. A classic sales query looks like this:

SELECT 
  product.brand_name, 
  SUM(order_facts.order_dollars) 
FROM 
  product, order_facts 
WHERE 
  product.product_key = order_facts.product_key 
GROUP BY 
  product.brand_name;

This query is safe because every order points to exactly one product, and in turn that product belongs to exactly one brand. Even if brands live in a separate snowflaked table (as shown in Chapter 7), the path from facts to brand is still a single chain—sometimes called a “grandparent–grandchild” relationship.

The first eight chapters rely on this one-to-many assumption. Real processes, however, often involve multiple participants. An order may be credited to two salespeople, a medical claim may cite three diagnoses, or a bank account may have four owners. When a fact can refer to more than one row in the same dimension, the original star pattern no longer guarantees correct aggregations.

3. What Is a Multi-Valued Dimension?

A multi-valued dimension is one that can take multiple values for a single fact. In other words, a fact row legitimately relates to two or more rows in the same dimension table. The salesrep dimension becomes multi-valued if several people collaborate on one order.

The fact table cannot hold an unknown number of salesrep foreign keys, and the salesrep table cannot store fact keys either because each salesperson will appear in many rows of ORDER_FACTS. We therefore need a new design technique.

4. Option 1: Simplify with Fixed Roles

The simplest workaround is to break the many-to-many relationship into several one-to-many relationships by assigning explicit roles. For orders, that means storing more than one salesrep key in the fact table—perhaps a primary_salesrep_key and a secondary_salesrep_key. Each key points to the same SALESREP table, but under a different role alias.

  1. Add one foreign key column per role you want to support.
  2. Create matching table aliases (Primary Salesrep, Secondary Salesrep, etc.) when you query.
  3. Populate unused roles with a default surrogate key that represents “not applicable.”

This approach keeps a pure one-to-many relationship, but two issues appear immediately:

  • Simple questions become complicated. To total sales for one salesperson you must filter on both foreign keys (or run two queries and merge them).
  • You can only store as many participants as you have columns. The first three-person order breaks the design unless you add yet another column and update every downstream report.
Tip: Simplifying a multi-valued relationship works only when collaboration is rare and the maximum number of participants is known and small. Expect additional reporting logic and accept that the solution stops working when a new record is set.

5. Option 2: Build a Bridge Table

When simplification is too limiting, create a bridge table that sits between the fact table and the dimension. The bridge stores groups of dimension members, and the fact table simply points to the appropriate group.

  1. Create a bridge table with a surrogate group_key plus a foreign key that points back to the dimension.
  2. Insert one row per member of the group, all sharing the same group_key.
  3. Store only the group_key in the fact table.
  4. When you query, join ORDER_FACTS → SALES_GROUP → SALESREP.

The ETL process must now manage groupings. When a collaboration occurs, the ETL flow must either reuse the existing group (if that exact combination already exists) or create a new group by assigning a fresh group_key and inserting one row per participant. Every fact—even one with a single salesperson—points to a group.

Compared to the simplification option, this design supports groups of any size and makes it easy to filter or group by individual salesrep attributes. The trade-off is a new danger: because one fact joins to multiple dimension rows, it is now possible to count the same fact twice.

Tip: Bridge tables restore flexibility and keep SQL simple, but they require disciplined ETL to build and govern the bridge and disciplined querying to avoid counting the same fact more than once.

6. Understanding Double-Counting

Note: In Chapter 9, “double-counting” is shorthand for any situation where a single fact row is counted two or more times, even if the actual multiplier is higher.

Bridge tables deliberately allow a fact to be associated with multiple dimension members. Sometimes that is exactly what you want. An “impact” report that totals order_dollars per salesperson should show Ann and Henry’s joint order inside both of their totals.

But the same query becomes wrong if it requests a grand total or if it groups by a non-unique attribute such as region. Consider this SQL:

SELECT 
  salesrep.region, 
  SUM(order_facts.order_dollars) 
FROM 
  salesrep, sales_group, order_facts 
WHERE 
  order_facts.sales_group_key = sales_group.sales_group_key 
  AND sales_group.salesrep_key = salesrep.salesrep_key 
GROUP BY 
  salesrep.region;

If Ann and Henry both belong to region “East,” the RDBMS joins the fact row to two salesrep rows, then groups by region. The single $1,000 order is now counted twice, and “East” incorrectly shows $2,000.

REGIONSUM(order_dollars)
East2,000 (Ann & Henry counted separately)
Tip: The only safe way to summarize data through a bridge is to group by a column that uniquely identifies each dimension member—typically the natural key or surrogate key—and to avoid exposing grand totals to casual users.

To keep analysts out of trouble, insist that impact-style reports always display detail at the dimension grain, and lock down widgets that add grand totals unless they first collapse the bridge using one of the mitigation techniques below.

7. Mitigating Double-Counting

7.1 Beware of Cosmetic Fixes

A tempting idea is to declare that each group will be used only once: if Ann and Henry collaborate again, create a brand-new group instead of reusing group 1. This turns the fact-to-bridge join into a one-to-many relationship, but it is one-to-many in the wrong direction. The fact row still points to two salesreps, so it can still be double-counted, and now the bridge table grows faster than the fact table because it stores duplicate combinations.

7.2 Use Allocation Factors Only When Business-Approved (Figure 9-5)

If the business can agree on how to apportion each fact across the participants, store that percentage in the bridge and multiply before aggregating.

  1. Add an allocation column to the bridge table.
  2. During ETL, have business rules (not IT guesses) populate the percentages so they add to 1.0 per group.
  3. Ensure every query multiplies the fact by the allocation before summing. Building a view that pre-joins the bridge can enforce this but adds overhead to queries that do not need the bridge.

Allocation factors are rare because they require policy decisions (“who gets credit?”) that can be politically fraught. Some facts—such as a quantity of 1 refrigerator—produce awkward fractions (Ann sells 0.75 of a refrigerator). Decide whether that is acceptable before adopting this method.

Tip: Only use allocations when the business already owns a clear, trusted rule. Always aggregate allocated facts (SUM(fact * allocation)), never allocate an already summed total.

7.3 Change the Fact Table Grain When Clean Allocations Already Exist

If the operational system already captures allocations, consider redefining the fact table’s grain. For example, load “order lines allocated to salesreps” instead of “orders.” Each row then already reflects the correct portion of the fact, and you can avoid the bridge entirely.

7.4 Safe Access via a Primary Member (Figure 9-6)

Another defensive tactic is to supplement the bridge with a traditional one-to-many relationship that names a single primary participant. Casual users rely on the primary key, while trained analysts can still join through the bridge when necessary.

Hide the bridge (and the tables that expand it) from self-service users. Direct them to the primary relationship, which cannot double-count. Only advanced analysts should be able to include the bridge, and they must follow the grouping guidance from Section 6.

Tip: Pair a bridge with at least one simplified path—either a primary member or an allocation view—so inexperienced users have an obvious safe route, while power users retain the flexibility they need.

8. Slow Changes and Bridge Tables

Slowly changing dimensions (SCDs) behave the same way here as elsewhere: a Type 1 change overwrites history, while a Type 2 change inserts a new row with a new surrogate key so historical facts still point to the older row.

8.1 Changes to Bridged Dimension Rows

  • Type 1: Update the dimension row in place. Existing bridge memberships continue to point to the same surrogate key, which is fine because history was meant to be overwritten.
  • Type 2: Insert a new dimension row and, the next time the collaboration happens, create a new group that references the new surrogate key. Past facts still point to the old group; new facts use the new group.

In the Ann-and-Henry example, a Type 2 change to Ann means we keep the old group for historical orders. When the updated Ann and Henry work together again, ETL creates a new group containing Ann’s new surrogate key plus Henry.

8.2 When the Group Itself Has Meaning

Some organizations treat the collaboration group as a named entity (“Eastern Special Project Team”). In that case you may add descriptive attributes and even a natural key to the bridge table. Apply Type 1 or Type 2 logic to those attributes just as you would for any dimension attribute: overwrite for Type 1, create a new group (new rows for every member) for Type 2.

Note: If the group is a well-defined business entity with its own attributes, consider modeling it as a true dimension and treating the participants as multi-valued attributes (see Section 10).

8.3 Membership Changes and Optional Time-Stamps

  • Type 1 membership change: Delete the departing member’s row in the bridge and insert rows for the new members. Past facts retroactively point to the new mix.
  • Type 2 membership change: Create an entirely new group and associate future facts with it. You may also capture effective_start_date / effective_end_date on the group rows (as discussed in Chapter 8) if you need a timeline of who served on the team.

Document the group handling clearly so ETL developers know when a change should reuse an existing group versus when it requires a new one.

9. Working with Restrictive Tools

Entity-relationship (ER) modeling rules forbid many-to-many relationships, so some design tools, BI semantic layers, or even database optimizers refuse to accept a join that is not backed by a primary-key/foreign-key constraint. A bridge violates that expectation because sales_group_key is not the primary key of SALES_GROUP (there are multiple rows per group).

This two-table pattern is functionally identical to the original bridge, but it satisfies tools that require every foreign key to point to a unique primary key. Another alternative is to leave out the relationship from the diagram and write the SQL manually, but that is rarely acceptable when you must document the model or configure a BI tool.

Tip: When a tool forbids many-to-many joins, split the bridge into a “group” table (one row per group) plus an intersect table (one row per member). It feels silly, but it keeps software happy without changing query results.

10. Multi-Valued Attributes in One Dimension

Sometimes the dimension itself is fine, but one of its attributes can repeat. Customers may have multiple phone numbers, bank accounts can list multiple owners, or a company may operate in several industries. These are multi-valued attributes.

10.1 Simplify with Fixed Attribute Columns (Figure 9-9)

Just as we tried with multiple salesrep roles, you can “flatten” the attribute into several columns such as industry_1, industry_2, and industry_3.

This technique only works when:

  • The business is comfortable with a hard limit on how many values will be stored.
  • Each slot has a clear role (home phone vs. office phone).
  • You will not need to filter or group facts by a value that could appear in any slot.
Tip: Flatten multi-valued attributes only when the repeating values are optional metadata, never when analysts must search or group by those values.

11. Designing an Attribute Bridge

When flattening is too limiting, move the repeating attributes into an outrigger table and use a bridge to associate each dimension row with one or more outrigger rows.

  1. Create an outrigger table for the repeating values (INDUSTRY, CONTACT_METHOD, etc.) with its own surrogate key.
  2. Build a bridge (group) table that stores group_key plus the outrigger’s surrogate key; insert one row per value in the group.
  3. Add a group_key foreign key to the main dimension table.
  4. During ETL, detect the combination of attribute values, look up (or create) the corresponding group, and store its key on the dimension row.

This design stores any number of attribute values and makes it easy to filter or group facts by the outrigger attributes. As with dimension bridges, the ETL process must create groups even when only one value exists.

Tip: Attribute bridges offer the same flexibility as dimension bridges, but they sit between a dimension and its outrigger instead of between a fact and a dimension.

12. Reporting Safely on Attribute Bridges

The same double-counting risks apply when you join a fact table to a dimension and then through an attribute bridge to an outrigger. Joining customer orders to industries duplicates any fact for customers with multiple industries.

SELECT 
  customer.customer_name, 
  industry.industry_name, 
  SUM(order_dollars) 
FROM 
  order_facts, customer, industry_group, industry 
WHERE 
  order_facts.customer_key = customer.customer_key 
  AND customer.industry_group_key = industry_group.industry_group_key 
  AND industry_group.industry_key = industry.industry_key 
GROUP BY 
  customer_name, industry_name;

If Company C spends $10,000 and participates in two industries, the result looks like this:

CUSTOMER_NAMEINDUSTRY_NAMESUM(order_dollars)
Company CManufacturing10,000
Company CServices10,000

This is perfect for an industry impact report but disastrous if someone clicks “Grand Total.”

To protect less-experienced users, mark exactly one primary member in each group (as shown in Figure 9-10) and expose a view that filters industry_group.primary_industry = 'Primary'. Power users can still access all rows, but most people see only the primary industry and cannot double-count.

Tip: Every query that traverses an attribute bridge risks double-counting. Provide a “primary member only” view for casual users and reserve the full bridge for trained analysts.
Note: SQL-generating BI tools may struggle when more than one join path exists between tables. Chapter 16 provides configuration guidance to keep semantic layers from misusing bridge tables.

Also consider removing the “Grand Total” button for any report that pulls in the bridge unless it is explicitly aggregating allocated values.

13. Managing Change for Attribute Bridges

13.1 Changes to the Outrigger

Changes to the outrigger’s rows ripple outward. A Type 1 change (rename an industry) simply updates the outrigger and keeps all group memberships intact. A Type 2 change (split “Services” into “Financial Services”) requires more work:

  • Insert a new row in the outrigger with the new surrogate key.
  • Create a new group that references the new key plus any unchanged values.
  • Create a new Type 2 row in the dimension so future facts can point to the new grouping while historical facts keep the old association.
Tip: A Type 2 change in an outrigger requires a Type 2 change in every related dimension row and a new group in the bridge.

13.2 Changes to Group Membership

If a customer leaves one industry and joins another:

  • Type 1 response: Update the dimension row to point to a different industry_group_key. Historical facts will now roll up under the new combination.
  • Type 2 response: Insert a new dimension row with a new surrogate key and new industry_group_key. Historical facts stay tied to the previous mix of industries.

Document industry_group_key (or any similar group reference) as a Type 2 attribute so ETL developers know that any change in group membership should usually trigger a new dimension row.

Tip: Treat changes to group membership as changes to the dimension itself; otherwise you silently rewrite history.

13.3 Changes Within the Dimension Row

If the dimension undergoes a Type 2 change that does not affect the multi-valued attribute (for example, the customer’s address changes but industries do not), the new row can reuse the same group_key. There is no need to duplicate groups unless the repeating attribute actually changes.

13.4 Where to Store Time-Stamps

Time-stamping the dimension row (for example, with effective_start_date / effective_end_date) already captures when a particular grouping applied. Adding time-stamps to the attribute bridge is redundant and forces you to create a separate group for every customer even when they share the same combination. Reserve bridge-level time-stamps for dimension bridges where the group itself is the thing you are tracking.

14. Additional Design Considerations

14.1 When the Outrigger Is Itself a Group

Bridge tables are sometimes described as “group tables,” which can be confusing when the outrigger already represents real-world groups (committees, unions, clubs). Keep terminology clear: the bridge is just an association table linking the dimension row to each group. The usual double-counting warnings still apply—if an employee belongs to three committees, facts tied to that employee will appear three times when you join to committees.

Tip: Avoid calling the bridge a “group” when the outrigger already represents groups. Think of it purely as an association table.

14.2 Folding the Outrigger into the Bridge

If only one or two attributes repeat, you may store them directly in the bridge table instead of creating a separate outrigger. This reduces the number of joins but requires you to enforce consistent spelling and indexing across the duplicated values.

14.3 Extra Ways to Resolve Many-to-Many Relationships (Figure 9-11)

The INDUSTRY_GROUP table is entirely redundant—the real work happens in GROUP_MEMBERSHIP—but its presence keeps strict tools satisfied. Another alternative (when tool constraints demand it) is to remove the group key from the dimension entirely and create an intersect table that stores customer_key and industry_key pairs. This eliminates the reusable groups but may result in a very large intersect table because each customer-industry combination needs its own row.

14.4 Bridge Tables Often Resemble Fact Tables

Because bridges store mostly keys (and sometimes allocation factors or flags), some tools treat them as factless fact tables (Chapter 12). That is acceptable, but remember that Chapter 4 warned against joining two fact tables because it can create a Cartesian product. Bridge tables are the exception: you want the duplication they introduce. Configure your BI tool so it knows this join is intentional, and be prepared for it to classify allocation percentages or primary-member flags as degenerate dimensions.

15. Key Takeaways

  • When a fact must link to multiple dimension members, you can sometimes simplify the problem by defining several one-to-many roles.
  • Such simplification complicates reporting and only supports a fixed number of participants.
  • Bridge tables let a fact relate to any number of dimension rows while keeping the SQL straightforward.
  • Bridges make it easy to double-count facts, so access and aggregation rules must be tightly controlled.
  • You can add allocation factors or a single “primary” relationship to keep casual usage safe.
  • If a tool cannot represent the many-to-many join, create an intersect table to resolve it.
  • Every bridge introduces new slow-change considerations for both attributes and relationships.
  • Attribute bridges behave like dimension bridges but sit between a dimension and an outrigger.
  • Some tools will interpret bridges as fact tables; that is acceptable as long as the tool does not automatically drill across them without safeguards.
  • Type 2 changes can cascade across dimensions, bridges, and outriggers, so plan ETL responses carefully.
